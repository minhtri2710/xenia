# AGENTS.md — xenia

xenia is a pre-launch online shop for wine and light grape wine: Next.js (App Router) with Payload 3 embedded, on Postgres. Vietnamese is the default locale at `/`; English mirrors it under `/en` with the same slugs.

## Commands

Setup from a fresh clone:

```sh
pnpm install
cp .env.example .env     # dev-only placeholders, never real secrets
pnpm db:up               # start Postgres (only needed for /admin, /api and pnpm dev with Payload)
```

| Command | What |
|---|---|
| `pnpm dev` | Dev server on http://localhost:3000 |
| `pnpm lint` | ESLint |
| `pnpm typecheck` | `tsc --noEmit` |
| `pnpm test` | Vitest unit tests (`src/**/*.test.ts` and `e2e/database.unit.ts`) |
| `pnpm seed` | Replaces the catalogue (producers, wines, vintages), gift `packaging` (`PACKAGING`) and `card-designs` (`CARD_DESIGNS`) with the fictional seed in `src/seed/data.ts`; sets owner information to visibly fictional `SAMPLE DATA` values, zones with fee and lead days (`ZONE_FEES`) and empty `blackoutDates` in `site-settings`. Deterministic content; it writes no other collection and creates or deletes no `users`, `orders` or `checkout-drafts` row, but deleting the old vintages clears `vintage` on existing order lines (the lines keep their snapshots; expiry restocks nothing for them). Needs `pnpm db:up`. |
| `pnpm test:e2e` | Playwright + axe. Starts its own `next dev` on **localhost:3417** and stops it afterwards. Needs `pnpm db:up`: `e2e/admin.spec.ts`, `e2e/checkout.spec.ts` and `e2e/account.spec.ts` (its V1 test, its administrator-token test and its D13.5 test) empty the `users` table with `TRUNCATE users CASCADE` (which reaches only Payload's own session and preference tables, never a customer, order or catalogue row) and create their own admin, and every spec that reads the catalogue runs `pnpm seed` in `beforeAll`, so no spec relies on existing data. Orders accumulate across runs (they are never deleted); the checkout spec counts orders before and after, never absolute. The specs' own SQL (`sql` in `e2e/support.ts`) targets the database named in `DATABASE_URI` (from `.env` unless the shell sets it) and fails fast when it is missing, so a scratch database redirects the server, the seed and the specs together. |
| `pnpm build` | Regenerates Payload's import map, then `next build`. Needs `.env` but no running database. |
| `pnpm payload generate:types` | Regenerate `src/payload-types.ts` after a collection change |

Check set, in order: `git diff --check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`, `pnpm build`.

## Ports

- 3000: `pnpm dev`.
- 3417: Playwright's server (`playwright.config.ts`), bound to `localhost`. It never reuses a running server, so a collision fails loudly. Do not bind dev servers with `--hostname 127.0.0.1`: Next builds `request.url` on `localhost`, next-intl's rewrites then look cross-origin and redirect-loop.
- 5437: Postgres, bound to 127.0.0.1 only. Ports 5432-5435 and 7784-7785 belong to other projects on this host; do not touch their containers.

## Postgres

- Start: `pnpm db:up` (`docker compose up -d --wait`). Container `xenia-dev-postgres`, data in the gitignored `.data/postgres`.
- Stop: `pnpm db:down`.
- Reset (dev data is disposable): `pnpm db:reset`.
- Schema management pre-launch: Payload's dev **push** (`@payloadcms/db-postgres` pushes the schema when `NODE_ENV` is not `production`). There is no `migrations/` directory. Reason: the schema changes every slice and dev data is disposable, so migrations would only record churn. The first deploy creates one baseline migration and switches to migrations from then on.

## Process rule

Every server and container a seat starts is stopped before it reports: dev servers by the pid it started, Postgres by `pnpm db:down`. Never stop a process or container you did not start.

## Pre-launch policy

One live contract and one implementation path. No compatibility layers, shims, aliases, dual paths, fallbacks for removed designs, or migrations for dev data. When the design changes, make the breaking change and update every caller and test.

## Age gate invariants (Decree 24/2020 Art. 6.1, Law 44/2019 Art. 16.3)

- The gate is `src/proxy.ts`, which runs on the server before any page renders. It redirects every storefront request without the marker cookie to `/xac-minh-tuoi` (or `/en/xac-minh-tuoi`) with the requested path in `next`, then hands everything else to next-intl's middleware.
- Exempt: `/xac-minh-tuoi`, `/tam-biet` and their `/en` equivalents, `/admin`, `/api` (Payload), `/_next` and `/_vercel`. Everything else is gated, including paths with a file extension. A new file in `public/` is gated unless its path is exempted in the proxy matcher.
- The form asks for a full name and a date of birth. A bare "I am 18+" button does not satisfy D4.
- Validation is on the server (`src/app/[locale]/xac-minh-tuoi/actions.ts`, `src/lib/age.ts`). Blank or whitespace-only name, unparseable date and future date of birth are field errors, not refusals.
- Adult: the visitor returns to the sanitised `next` path. Under 18: redirected to `/tam-biet` with no marker. There is no lockout.
- Age rule (`isAdult` in `src/lib/age.ts`): computed on the calendar date in `Asia/Ho_Chi_Minh`, never server-local or UTC. The 18th birthday is adult. A 29 February birthday reaches 18 on 1 March in a non-leap year.
- Return path (`src/lib/return-path.ts`): only same-origin relative paths. A missing or empty `next`, absolute URLs, `//host`, backslashes, control characters and `javascript:` become the home of the gate's locale: `/` for vi, `/en` for en.
- Privacy: the declared name and date of birth are never persisted — no database, log, cookie value or analytics. The marker cookie `xenia_age_ok=1` carries no personal data, is `HttpOnly`, `SameSite=Lax`, `Secure` in production, and lasts for the browser session. A forged marker is an accepted residual (equal to a false self-declaration); do not add signing or eKYC.
- The notice `Không bán rượu, bia cho người chưa đủ 18 tuổi` (Law 44 Art. 32.5) is in the storefront layout footer on every page; `/en` shows an English translation beside it and marks the Vietnamese notice with `lang="vi"`.

## Policies, site settings, header and footer

- Nine policy pages live at `/chinh-sach/{thong-tin-doanh-nghiep,bao-mat,dieu-khoan,khieu-nai,gia,dieu-kien-ban-hang,thanh-toan,giao-hang,doi-tra-hoan-tien}` and the same slugs under `/en`. There is no policy index page. `src/lib/policies.ts` is the canonical route list; `src/app/[locale]/chinh-sach/[slug]/page.tsx` rejects unknown slugs and reads policy-relevant settings per request. They remain behind the unchanged age gate.
- These pages are explicitly pre-launch drafts, not legal advice or compliance claims. All show a notice that legal review is pending. Do not remove or weaken this notice until the Human records counsel's review. Counsel questions Q4 (failed ID check), Q10 (micro-business retention), Q12 (geographic scope), Q13 (guest status links), and Q-draft (pre-consent checkout-draft storage) remain unresolved and are marked pending in policy copy; do not invent answers.
- Enforced policy facts come from their implementation source: age from `LEGAL_AGE`, payment methods from `PAYMENT_METHODS`, order retention from `ORDER_RETENTION_YEARS`, draft lifetime from `DRAFT_TTL_HOURS`, message size from `MAX_MESSAGE_CODE_POINTS`, windows/horizon from `DELIVERY_WINDOWS`/`HORIZON_DAYS`, VAT from `VAT_RATE_PCT`, cookies from their cookie constants, and delivery zones/fees/lead days from `site-settings`. Do not duplicate enforced values as independent literals in policy copy.
- `site-settings` remains admin-only (`adminOnlyGlobalAccess`, `src/lib/access.ts`; no public `access`). Its owner group contains legal name, head office, legal representative, business registration number/date/place, alcohol retail licence number/issuer/date, contact email and phone, and an optional HTTPS-only notification link. Storefront code reads it through Payload Local API on the server; the footer and policy facts are request-fresh.
- The global footer is on every storefront page, including the age gate and exit page. It renders the owner/contact information from `site-settings`, the notification link only when set (plain HTTPS link, no image), all nine policy links, and the L19 notice.
- The header's primary nav links to wine catalogue, gift collections (`/qua-tang`), gift service and cart, then the account link ("Đăng nhập" to `/tai-khoan/dang-nhap` when signed out, "Tài khoản" to `/tai-khoan` when signed in). The language link switches the same pathname and query between vi and en.
- Accessibility: the layout includes a skip link to focusable `#main-content` and a visible `:focus-visible` outline. E2E checks use `expectNoSeriousA11yViolations`, which includes a 360 px horizontal-overflow check; English pages identify the Vietnamese legal notice with `lang="vi"`.

## Catalogue

- Collections in `src/collections/catalogue.ts`: `producers`, `wines`, `vintages`, localized vi (default) and en with `fallback: false`. Vocabularies (types, countries, occasions, pairings, bottle sizes) live in `src/lib/catalogue.ts`.
- Access: the catalogue collections set `access: adminOnlyAccess` (`src/lib/access.ts`), so every operation over `/api` needs an authenticated `users` (admin) user. Payload's default, "any signed-in user", is not used: a `customers` session would satisfy it. Do not add a public `read`: `/api` is exempt from the age gate, so a public read would hand product information to an undeclared visitor (Decree 24/2020 Art. 6.1, D4). The storefront reads through Payload's Local API on the server (`src/lib/catalogue-data.ts`). GraphQL has no route (`src/app/(payload)/api` has only the REST catch-all). `e2e/catalogue.spec.ts` checks unauthenticated REST and `/api/graphql` return no catalogue data.
- Published: a wine with `status: published` that has at least one `published` vintage. The collection page lists only those.
- ≥15° restriction (Law 44/2019 Art. 5.7 and 5.9): a vintage at 15% ABV or above may not be advertised or promoted. `isAdRestricted(abvPct)` in `src/lib/catalogue.ts` (`abvPct >= 15`, per vintage) is the only definition. It is derived on read and never stored: no column, no stored field, no seed value. The admin shows it as the read-only `adRestricted` virtual field on vintages (list column and edit view), computed by an `afterRead` hook.
- Every future promotional surface (banner, featured placement, sale price, discount, gift-with-purchase, free wrap) must exclude restricted vintages through `isAdRestricted`. A surface that promotes a whole wine treats it as restricted when any of its published vintages is. The only such surface today is `/qua-tang` (below); `/ruou-vang` stays a neutral browse.
- Gift collections `/qua-tang` (and `/en/qua-tang`, same slug): gated and rendered per request. One collection per gift occasion (`GIFT_OCCASIONS`: `gift`, `tet`, `celebration`), taken from each wine's admin-set `occasions`; `dinner` and `everyday` make no collection. A wine tagged with several gift occasions is listed in each. The budget is the URL query `?price=<band id>` over `PRICE_BANDS`, its options are plain links, and an unknown value is ignored; cards follow `/ruou-vang` (a wine matches a band when one of its published vintages is in it, the "from" price is the lowest matching, the out-of-stock label is the same) and link to `/ruou-vang/<slug>`. The pure `giftCollections` (`src/lib/catalogue.ts`) lists a wine only when `isRestrictedWine` is false, which is `isAdRestricted` over every published vintage of the wine, whatever the band; `loadCatalogue` carries each published vintage's `abvPct` for it, read on request and never stored. The page shows the warning `Người dưới 18 tuổi không được uống rượu, bia` as fixed wording (like the footer notice, not from `LEGAL_AGE`), with `lang="vi"` and an English translation beside it on `/en`; this is a conservative measure, not a compliance claim, and counsel Q6 and Q7 stay pending. It mentions wrap only as the paid gift service, with a link to `/dich-vu-goi-qua`, and has no sale, discount, free or gift-with-purchase wording. Any future copy or surface there stays under the promotional-surface rule above.
- Collection page `/ruou-vang`: facet and sort state is the URL query, applied on the server by the pure `listWines` in `src/lib/catalogue.ts`. Facets are plain links, so they work without client JS. Size and price band are vintage facets: a wine matches when one of its published vintages satisfies both, and the card's "from" price is the lowest price among the matching vintages.
- Collection cards link to the product page and carry an active `size` facet as `?size=`.
- Product page `/ruou-vang/<slug>` (and `/en/ruou-vang/<slug>`, same slug): rendered per request from `loadWine` in `src/lib/catalogue-data.ts` (Local API). A draft wine, an unknown slug and a published wine with no published vintage render the not-found page with HTTP 404.
- Selector query `?vintage=<year|nv>&size=<ml>`, resolved on the server by the pure `selectVintage` in `src/lib/vintage-selection.ts`, the one place that drops draft vintages. Options are plain links, so they work without client JS. Default: the most recent published vintage (years newest first, NV after every year) in 750 ml, or its smallest size when it has no 750 ml. An unknown or unavailable value never errors: an invalid `vintage` resolves to the most recent vintage that has the requested `size`, else the default vintage; a `size` the chosen vintage lacks resolves to that vintage's default size.
- The spec list shows, for the selected vintage: producer, vintage or NV, country, region, appellation (when set), grapes with shares, ABV as `% vol`, volume, drinking window (when set), importer, serving temperature, tasting note, the four-axis profile as text, pairings, price (VND, VAT included) and stock state. It shows no occasions, awards or promotional copy. Below the selector, an add-to-cart form (quantity, capped at stock) adds the selected vintage when it has stock.
- Price bands (integer VND, VAT included; lower bound inclusive, upper exclusive): under 1 000 000; 1 000 000 to under 2 000 000; 2 000 000 to under 4 000 000; 4 000 000 and over.
- Images are placeholders drawn in CSS. There is no `public/` directory.

## Cart, checkout and orders

- Routes: cart `/gio-hang`; checkout step 1 buyer `/thanh-toan`, step 2 delivery `/thanh-toan/giao-hang`, step 3 gift options `/thanh-toan/goi-qua`, step 4 review and consent `/thanh-toan/xac-nhan`; order status and mock payment `/don-hang/<token>`. All gated like every storefront route, same slugs under `/en`, rendered per request. A step with an empty cart redirects to the cart; a step without its earlier steps redirects to the first missing one.
- Cart: the `xenia_cart` cookie holds only vintage ids and quantities (`[{v, q}]`, at most 20 lines), never a price or personal data. `HttpOnly`, `SameSite=Lax`, `Secure` in production, browser session. Every read resolves it against the database with the pure `normalizeCart` (`src/lib/cart.ts`): unknown, draft (vintage or wine) and out-of-stock vintages are dropped and quantities capped at stock. Adding is allowed only for a published vintage of a published wine with stock.
- Checkout state between steps: a server-side draft in the `checkout-drafts` collection (admin-only through `adminOnlyAccess`, `admin.hidden`; structured fields only). It holds the idempotency key `clientKey` (a v4 UUID), the validated buyer, `attestedAt`, the delivery (step 2) and the gift choice (step 3); never the date of birth. The `xenia_checkout` cookie (same attributes as the cart, `path=/`) carries only the draft's `handle`: 32 bytes from the CSPRNG as base64url (43 characters), in a unique column, never rendered, posted or logged. `readCheckout`, `writeCheckout` and `clearCheckout` in `src/lib/shop-data.ts` are the only entry points (placement reads and deletes the draft by the same handle inside its transaction, through `src/lib/checkout-drafts.ts`). A read matches the handle with `equals` and `expiresAt` later than now in one query; an unknown and an expired handle are the same absent result, and the draft is re-validated (`parseCheckout`). A write never reuses a handle it did not find live. Retention: a draft expires 24 h after its last write (`expiresAt`, indexed); every write first deletes every expired draft; placement deletes the draft in its transaction; the under-18 refusal deletes it. A forged `attestedAt` is the same accepted residual as a forged gate marker.
- Step 1 (Decree 24/2020 Art. 6.1): the server validates every field (`checkBuyer`, `src/lib/buyer.ts`) and re-checks age with `isAdult`. Under 18: no order, the marker and checkout cookies are deleted, redirect to `/tam-biet` (locale-aware). The date of birth is never stored: no column, log or cookie; the order keeps `ageAttestedAt` only.
- Step 2: mode `self` (to the buyer's address) or `gift` (to a recipient whose name, phone and address are validated with the buyer's contact rules, `checkRecipient`). Self mode shows the courier ID-check rule (Decree 24/2020 Art. 6.3); gift mode, here and at step 4, states that the recipient must be 18 or over and show ID or the courier does not hand the gift over (D6). Every order has a date and a window (morning, afternoon, evening). `src/lib/delivery.ts` is the only date rule and takes the instant as a parameter: earliest = today in `Asia/Ho_Chi_Minh` (`vietnamToday`) + the zone's `leadDays`; latest = earliest + 30 (`HORIZON_DAYS`); a date in `blackoutDates` is refused. The `site-settings` global (admin-only; read through the Local API) holds `zones` (fee and `leadDays`, a whole number ≥ 1) and `blackoutDates` (YYYY-MM-DD). Changing the mode drops the step 3 choice.
- Step 3: packaging for every order: none (default) or one active packaging for the whole order that fits every bottle size in the cart; only fitting packaging is offered, and a forged unknown, inactive or non-fitting one is refused. Wrap units = ceil(bottles / capacity) (`wrapUnits`, `src/lib/gift.ts`). Card, message, sender and hide prices exist only in gift mode; in self mode they are neither shown nor accepted. Message (`checkMessage`): CR and CRLF become LF, then NFC once at this boundary; at most 250 code points after NFC; no control character except LF; empty allowed; the normalized value is stored. The sender is prefilled with the buyer's name or is anonymous. Hide prices defaults on in gift mode. Wrap is a paid service: `priceVnd` is at least 1 (no free wrap), and any promotion on it falls under the promotional-surface rule above.
- Step 4 (Law 122 Art. 12): goods and quantities, the delivery mode, recipient, date and window, the wrap line (`Gói quà: <units> × <name> = <amount>`), in gift mode the card, message, sender or anonymous and hide prices, the cashless payment methods, goods, wrap, shipping, total and the VAT included, an edit link to each earlier step, and two unticked required consents (terms, privacy). The form posts the review's digest (`orderDigest`, `src/lib/order-digest.ts`): SHA-256 of the lines sorted by vintage id as vintage id, qty and unit price, the buyer (name, phone, email, address, exactly as stored in the checkout state), the zone, its fee, the mode, the recipient (name, phone, address), date and window, the wrap (packaging code, vi and en names, units, unit price), the gift (card code and vi and en names, message, sender or null for anonymous, hide prices), and goods, wrap, shipping, VAT included and total, then the id of the signed-in account or null for a guest (last). `reviewOrder` (`src/lib/order-review.ts`) computes it once for both the review and placement. It is not a secret. The consent links point at the terms and privacy policy pages, `/chinh-sach/dieu-khoan` and `/chinh-sach/bao-mat`.
- Totals: `computeTotals` in `src/lib/order-totals.ts` is the only arithmetic, in integer VND: goods = Σ qty × unit price; wrap = units × the packaging's unit price (0 without packaging); shipping = the zone fee; total = goods + wrap + shipping; VAT included = total × 10 / 110 rounded to the nearest whole VND (a tie cannot occur). Non-integer or negative inputs throw. The review and placement recompute on the server from stored prices and the fee; no posted or cookie price, fee, wrap price, units or total is ever read.
- Placement (`placeOrder`, `src/lib/place-order.ts`): one server action, one database transaction through the Local API. Every line is re-read (published vintage and wine, stock), and the unit price, ABV and vi and en wine names are snapshotted. The packaging (active, fits, price) and card (active) are re-read and the date re-checked at the placement instant; a packaging or card that is no longer available refuses back to step 3, and a date that is no longer valid refuses back to step 2, each with a field error. The mode, recipient, date, window, packaging code, names, units and unit price, card code and names, message, sender or anonymous, and hide prices are snapshotted. A missing, draft or over-stock line refuses the whole order with a per-line field error, and the cart is rewritten to what is available so the next review is accurate. Placement places exactly what step 4 showed (Law 122 Art. 12): it recomputes the digest from its snapshots, the buyer it stores, zone, fee and totals, and a mismatch (a quantity, line, unit price, buyer detail or address, zone or fee, recipient, date, window, packaging or its price, card, message, sender or hide prices changed after the review) rolls back and re-shows step 4 at `?changed=1` with the current values, a notice that the order changed, and unticked consents. No amount changes silently; a forged digest can only fail to match.
- Stock: decremented at placement, in the transaction, with an atomic `stock = stock - qty` in vintage-id order. The Postgres CHECK `vintages_stock_non_negative` (added in `src/payload.config.ts` `afterSchemaInit`) refuses a concurrent oversell. An unpaid `placed` order holds its stock for `PAYMENT_HOLD_MINUTES` from placement; `paymentDueAt` is stored and indexed. `releaseExpiredOrders(now)` runs before every storefront stock read or decision and every payment attempt; the admin shows stored stock. The release runs in one transaction and selects every unpaid placed order with `payment_due_at <= now`, marks each `expired` with a conditional status/payment update, then restocks its lines with atomic `stock = stock + qty` in vintage-id order. A line whose vintage was deleted has no stock to restore and is skipped; the order still expires. This release query is the only deadline boundary; the `expired` select option is excluded with Payload `filterOptions`, while the full lifecycle enum remains intact. Competing payment/release operations cannot both win; stock is restored once. A failed mock payment before the deadline keeps the order `placed` and stock reserved so the buyer can retry. Restocking a `cancelled` order remains an admin stock edit.
- Idempotency: the checkout state's key (a v4 UUID) is posted with the review form. Placement first returns any order with that `clientKey`, whatever the posted digest; the unique index on `clientKey` makes a concurrent duplicate roll back and return the winner. Every refusal after the transaction starts (a line problem, the stock CHECK, a changed order) first looks the key up again and returns the winner when one exists, so a duplicate that lost at the stock edge never rewrites the cart. Double submit, back-and-resubmit and a replayed POST all land on the one order.
- Status link: `/don-hang/<token>`, token = 32 bytes from the CSPRNG as base64url (43 characters), stored in a unique column for lookup, hidden in the admin, never logged by the app. A malformed or unknown token is a 404. The page is `noindex` and sets the `no-referrer` referrer policy.
- Order number: `XN-XXXX-XXXX`, 40 random bits in Crockford base32, unique column; a collision fails placement closed.
- Payment (Law 44/2019 Art. 16.4): mock only, no provider, key, webhook or network call. The method enum is exactly `vietqr_mock` and `card_mock`; there is no cash-on-delivery value anywhere. No card or bank account number is ever asked for. Each attempt runs `releaseExpiredOrders` in its own transaction at the attempt instant, then records payment with a conditional placed/unpaid status guard and no second deadline predicate; an `expired` order is refused with a visible message and never marked paid. Success marks a still-current `placed` order `paid`; failure before the deadline records `payment.status = failed` and leaves the order `placed` for retry. The status page shows the deadline while payable and an expired message without payment action after expiry.
- `packaging` (code, vi and en name and description, capacity, bottle sizes it fits, `priceVnd` ≥ 1, active) and `card-designs` (code, vi and en name, active) set `access: adminOnlyAccess`: admin-only like the catalogue; the storefront reads them through the Local API.
- Gift service page `/dich-vu-goi-qua` (and `/en`), gated and rendered per request: the active packaging with capacity, sizes, price (VAT included) and a CSS placeholder, the card designs, the message rule, the recipient 18+ and ID rule, and that wrap is paid with no free tier. It shows no wine or product. Step 3 links to it.
- `orders` (Law 122 Art. 16.2b): `adminOnlyAccess`; `create` is closed over REST and in the admin (placement is the only path); `delete` is closed and a `beforeDelete` hook refuses every delete, Local API included, including expired orders. `totals.wrapVnd` joins the totals. The lifecycle statuses are placed, paid, packed, out_for_delivery, delivered, id_check_failed, cancelled, returned and `expired`. The admin status select uses the full lifecycle enum with `filterOptions` excluding `expired`, which Payload validation also refuses; a server hook refuses any change to an already expired order. Every snapshot field, including indexed `paymentDueAt`, has field-level `update: false`.

## Accounts

- An account is optional; guest checkout is unchanged. `customers` (`src/collections/customers.ts`) is a second Payload auth collection with verify and lockout. It holds email, password (hash and salt are Payload's and never shown), `name`, `phone`, `address` and the consent record (`consents.terms`, `consents.privacy`, `consents.at`). It never holds a date of birth. It has no REST or GraphQL surface (`endpoints: false`, `graphQL: false`), so the admin lists customers read-only and cannot edit or delete one; `create`, `update` and `delete` are closed to everyone and the storefront writes through the Local API.
- Access (D1): one rule, `adminOnly` in `src/lib/access.ts` (the request's user belongs to `users`), on every collection and on `site-settings`. `orders` `create` and `delete` stay closed. Every collection and the global set `lockDocuments: false`, so Payload's `payload-locked-documents` collection, whose access is "any signed-in user", does not exist. `payload-preferences` still uses Payload's default and lets a customer's token read and write that customer's own preference rows; that is an accepted residual. `e2e/account.spec.ts` builds its `/api` table from the configured collection and global slugs, with a customer's token as a cookie and as a JWT header, and `src/lib/access.test.ts` does the same against the sanitized config.
- Session: the `xenia_account` cookie (`ACCOUNT_COOKIE`, `src/lib/accounts.ts`; the shared `cookieOptions`) holds Payload's JWT for a `customers` user; it is not `payload-token`. `currentCustomer` (`src/lib/account-data.ts`) accepts only a `customers` user, so an admin's token is never a storefront session. Sessions last `SESSION_SECONDS`. Sign-out removes the session on the server (`logoutOperation`), so a copied cookie stops working. A password reset or change ends every other session of the account (`endAllSessions`).
- Routes, all gated, `noindex` and rendered per request: `/tai-khoan` (profile, the account's own orders, password change, sign-out, deletion with the password), `/tai-khoan/dang-ky`, `/tai-khoan/dang-nhap` (with the "send the verification email again" form, which needs the email and the password), `/tai-khoan/xac-minh`, `/tai-khoan/quen-mat-khau`, `/tai-khoan/dat-lai-mat-khau`, and the same paths under `/en`. The token pages (`xac-minh`, `dat-lai-mat-khau`) set `no-referrer`; the token is spent by a button, not by opening the link.
- Registration asks for a date of birth and checks it with `isAdult` (as at checkout step 1; under 18: no account, the marker and checkout cookies are deleted, redirect to `/tam-biet`). The date of birth is never stored. Two unticked required consents (terms, privacy). A new and an existing email get the same answer; an existing one is mailed a notice. Sign-in works for verified accounts only and has one generic failure. The reset and resend answers are the same for every email. The reset link expires after `RESET_EXPIRY_MINUTES` and works once. The password is `PASSWORD_MIN_CODE_POINTS` to `PASSWORD_MAX_CODE_POINTS` code points and is not trimmed. `MAX_LOGIN_ATTEMPTS` wrong passwords lock the account for `LOCK_MINUTES` (an accepted residual: anyone can lock a known account for that long).
- Mail is a pre-launch mock. The email adapter (`mockEmailAdapter`, `src/lib/outbox.ts`) writes one `mock-outbox` row per message and makes no network call; it refuses when `NODE_ENV` is `production`; every send first deletes rows older than `OUTBOX_TTL_HOURS`. The admin shows the outbox read-only. Mail is in the request locale and links to the same locale as a relative path (no site URL is configured). A real provider needs the Human's decision first.
- Orders: `orders.customer` is an indexed, `update: false` relationship, set only when the order is placed while signed in. Deleting an account removes the row; its orders stay and lose the link. There is no linking by matching email anywhere: a guest order is never attached to an account. Step 1 is prefilled from the profile (still editable; the date of birth is asked again). Step 4 shows the account or "guest", and the account id is in `orderDigest`, so signing in or out after the review re-shows step 4 at `?changed=1`.
- Accepted residuals: registration's timing differs between a new and an existing email; someone else's unverified registration of an email occupies it until it is verified or deleted; the verification token does not expire.

## Conventions

- All UI copy lives in `messages/vi.json` and `messages/en.json`. `src/i18n/messages.test.ts` fails on hardcoded JSX copy under `src/app/[locale]`.
- Mood B (ivory editorial): tokens in `src/app/globals.css`. Fonts are Cormorant Garamond (display) and Be Vietnam Pro (body), self-hosted from `@fontsource` packages; both carry the Vietnamese subset.
- No runtime request to any third-party origin (fonts, analytics, embeds). No images of people; no competitor content.
- Payload admin lives at `/admin` and is not behind the gate.
- The admin makes no third-party request either: `admin.avatar` is `"default"` (Payload's default is Gravatar). `e2e/admin.spec.ts` fails on any non-localhost http(s) request or ws(s) connection in create-first-user and the view it lands on after registration, `/admin/account`, the producers, wines and vintages lists (and the ABV filters on vintages), a tawny vintage's edit view, the packaging and card-designs lists with one edit view each, the site-settings global, the customers list with one customer's view, the mock-outbox list with one message's view, and logout and login. Every third-party check uses `blockThirdParty` in `e2e/support.ts`, which watches both.
- Payload's code and JSON field editors load Monaco from `cdn.jsdelivr.net`, and Payload has no setting to self-host it. A slice that adds a `code` or `json` field must first make Monaco load without a third-party origin, or not use the field.
